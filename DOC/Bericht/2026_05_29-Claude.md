## 1. Code-Review — Gefundene Probleme

### 1.1 NullPointerException in `ListArticlesHandler.java`

**Problem:** Das DTO-Mapping rief `article.getPrice().toString()` und `article.getStock().longValue()` auf, ohne vorher zu prüfen, ob die Werte `null` sind. Da `price` und `stock` als `Integer` typisiert sind und in DynamoDB optional gespeichert werden, führte dies bei Artikeln ohne Preis oder Bestand zu einem `NullPointerException` zur Laufzeit.

**Fix:** Null-Checks eingebaut:
```java
article.getPrice() != null ? article.getPrice().toString() : null
article.getStock() != null ? article.getStock().longValue() : null
```

### 1.2 Fehlender No-Arg-Konstruktor in `Catalog.java`

**Problem:** Der AWS DynamoDB Enhanced Client instanziiert Modell-Klassen über Reflection. Dafür ist zwingend ein parameterloser Konstruktor erforderlich. In `Catalog.java` fehlte dieser — was beim Aufruf der Katalog-Endpunkte zu einem Laufzeitfehler geführt hätte.

**Fix:** Öffentlichen No-Arg-Konstruktor hinzugefügt:
```java
public Catalog() {}
```

### 1.3 Falsch angelegtes DynamoDB-Schlüsselschema in `Catalog.java`

**Problem:** Das Modell verwendete `catalogId` als `@DynamoDbPartitionKey`. In der tatsächlichen DynamoDB-Tabelle wird aber ein Single-Table Design verwendet: `partitionKey = "CATALOGS"` und `sortKey = "CATALOGS#<NAME>#METADATA#<uuid>"`. Ein dediziertes `catalogId`-Attribut existiert in der Datenbank **nicht** — es wird aus dem `sortKey` extrahiert.

**Fix:** Vollständiger Umbau des Modells auf das korrekte Key-Schema. `@DynamoDbIgnore` auf `getCatalogId()` gesetzt.

### 1.4 Defekte Methode `RequestBuilder.buildItemResponse()`

**Problem:** Die Methode enthielt einen `TODO`-Kommentar und sendete trotzdem einen unvollständigen (defekten) DynamoDB-Request ab, ohne den Aufrufer darüber zu informieren. Dieses stille Fehlverhalten ist schwer zu debuggen.

**Fix:** Methode wirft jetzt explizit eine `UnsupportedOperationException` mit erklärendem Text, solange sie nicht implementiert ist.

## 2. Neue Infrastruktur-Klassen

### 2.1 `DynamoDbClientFactory.java`

**Pfad:** `asset-service/src/main/java/com/sakai/inventory/api/infrastructure/DynamoDbClientFactory.java`

**Zweck:** Zentrale Singleton-Instanz für `DynamoDbClient` und `DynamoDbEnhancedClient`. Verhindert, dass jeder Lambda-Handler seinen eigenen Client aufbaut (ineffizient, teuer im Kaltstart).

Der Client liest die AWS-Region aus der Umgebungsvariable `REGION` (Standardwert: `eu-central-1`).

### 2.2 `KeyHelper.java`

**Pfad:** `asset-service/src/main/java/com/sakai/inventory/api/infrastructure/KeyHelper.java`

**Zweck:** Hilfsklasse für die Arbeit mit DynamoDB-Schlüsseln im Single-Table Design.

**Methoden:**
- `extractId(sortKey)` — Extrahiert die UUID aus dem letzten `#`-Segment des `sortKey`
- `findArticleById(table, id)` — Query auf `partitionKey = "ARTICLES"` mit FilterExpression `contains(#sk, :id)`
- `findCatalogById(table, id)` — Gleiche Logik für Kataloge

**Hintergrund:** Da bei API-Aufrufen nur die UUID bekannt ist (nicht der vollständige `sortKey`), kann `getItem()` nicht direkt verwendet werden. Stattdessen wird eine Query ausgeführt und das Ergebnis via `contains()` gefiltert.

## 3. Neue REST-Endpunkte (BE-06 bis BE-17)

Alle Handler liegen unter:  
`asset-service/src/main/java/com/sakai/inventory/api/handler/`

### Artikel-Endpunkte

| Endpunkt | Handler | Beschreibung |
|---|---|---|
| `GET /articles` | `ListArticlesHandler` | Alle Artikel abrufen, optional mit Query-Parametern filtern |
| `GET /articles/{id}` | `GetArticleHandler` | Einzelnen Artikel per UUID abrufen |
| `POST /articles` | `CreateArticleHandler` | Neuen Artikel anlegen |
| `PUT /articles/{id}` | `UpdateArticleHandler` | Artikel teilweise aktualisieren (Partial Update) |
| `DELETE /articles/{id}` | `DeleteArticleHandler` | Artikel löschen |

### Katalog-Endpunkte

| Endpunkt | Handler | Beschreibung |
|---|---|---|
| `GET /catalogs` | `ListCatalogsHandler` | Alle Kataloge abrufen |
| `GET /catalogs/{id}` | `GetCatalogHandler` | Einzelnen Katalog per UUID abrufen |
| `POST /catalogs` | `CreateCatalogHandler` | Neuen Katalog anlegen |
| `PUT /catalogs/{id}` | `UpdateCatalogHandler` | Katalog teilweise aktualisieren |
| `DELETE /catalogs/{id}` | `DeleteCatalogHandler` | Katalog löschen |

### Relation-Endpunkte

| Endpunkt | Handler | Beschreibung |
|---|---|---|
| `POST /catalogs/{id}/articles` | `AssignArticleToCatalogHandler` | Artikel einem Katalog zuweisen |
| `DELETE /catalogs/{id}/articles/{articleId}` | `RemoveArticleFromCatalogHandler` | Artikel aus Katalog entfernen |

### Implementierungsdetails

**Partial Update (`PUT`-Endpunkte):**  
Alle Update-Handler verwenden `ignoreNulls(true)` beim `UpdateItemEnhancedRequest`. Das bedeutet: Nur explizit gesetzte Felder im Request-Body werden in DynamoDB überschrieben. Felder, die im Body fehlen, bleiben unverändert.

**Suche nach ID:**  
Da bei einem API-Aufruf wie `GET /articles/199ac913-...` nur die UUID bekannt ist, aber DynamoDB den vollständigen `sortKey` (`ARTICLES#ART-001#SKU-7001#199ac913-...`) benötigt, wird immer eine Query + FilterExpression `contains(sortKey, uuid)` durchgeführt. Die Handler nutzen dafür `KeyHelper.findArticleById()` / `findCatalogById()`.

**Relation-Handler:**  
`AssignArticleToCatalogHandler` setzt `catalogId` am Artikel und erhöht `productCount` am Katalog. `RemoveArticleFromCatalogHandler` leert `catalogId` und verringert `productCount` (Minimalwert 0). **Hinweis:** Diese Operationen sind nicht atomar — bei gleichzeitigen Zugriffen kann `productCount` kurzzeitig inkonsistent sein.

## 4. Neue DTOs (Request-Objekte)

**Pfad:** `asset-service/src/main/java/com/sakai/inventory/api/dto/`

Alle DTOs sind als **Java Records** implementiert (unveränderlich, kompakt, kein Boilerplate).

| Klasse | Verwendung |
|---|---|
| `CreateArticleRequest` | Body für `POST /articles` — Pflichtfelder: `name`, `sku` |
| `UpdateArticleRequest` | Body für `PUT /articles/{id}` — alle Felder optional |
| `CreateCatalogRequest` | Body für `POST /catalogs` — Pflichtfelder: `name`, `color` |
| `UpdateCatalogRequest` | Body für `PUT /catalogs/{id}` — alle Felder optional |

**Validierung `color`:** Der Hexcode wird gegen `^#([A-Fa-f0-9]{6}|[A-Fa-f0-9]{3})$` geprüft. Bei ungültigem Wert: HTTP 400.

## 5. Anpassungen an `template.yaml`

**Pfad:** `template.yaml` (Projektroot)

### 5.1 DynamoDB-Tabelle entfernt

Die ursprüngliche `InventoryTable`-Ressource im SAM-Template wurde entfernt. Die Tabelle wird durch **AWS CDK** in einem separaten Stack verwaltet und existiert bereits in der Zielumgebung. Ein doppeltes Anlegen würde zu Deployment-Fehlern führen.

### 5.2 Tabellenname als Literal

`TABLE_NAME` wurde von `!Ref InventoryTable` auf den Literal-Wert `InventoryTable-Dev` umgestellt, da die CDK-verwaltete Tabelle nicht mehr als SAM-Ressource referenzierbar ist.

### 5.3 GSI-Referenzen entfernt

Der ursprünglich geplante GSI `SKU-index` ist in der CDK-Tabelle nicht vorhanden. Alle IAM-Berechtigungen wurden auf die reine Tabellenebene beschränkt.

### 5.4 Zwei IAM-Rollen

| Rolle | Zugewiesen an | Berechtigungen |
|---|---|---|
| `ReadOnlyRole` | List- und Get-Handler | `DescribeTable`, `Query`, `Scan`, `GetItem` |
| `ReadWriteRole` | Create-, Update-, Delete-, Assign-Handler | + `PutItem`, `UpdateItem`, `DeleteItem` |

### 5.5 CORS erweitert

CORS-Konfiguration in API Gateway wurde um `POST`, `PUT`, `DELETE` ergänzt (vorher nur `GET`).

### 5.6 Alle 12 Lambda-Funktionen registriert

Für jeden Endpunkt wurde eine eigene Lambda-Funktion mit korrektem Handler-Klassenname, Event-Trigger (API Gateway Method + Path), Timeout (30s) und IAM-Rolle definiert.

## 6. Anpassungen nach Testdaten-Analyse

Die Datei `asset-service/events/exhibition-items.json` enthält die tatsächlichen Testdaten für die DynamoDB-Tabelle. Die Analyse dieser Daten zeigte, dass die erste Implementierung der Handler auf falschen Key-Annahmen beruhte.

### Ursprünglich (falsch)
```
partitionKey = "ARTCL"
sortKey      = "ARTCL#<uuid>"

partitionKey = "CAT"
sortKey      = "CAT#<uuid>"
```

### Korrigiert (laut Testdaten)
```
partitionKey = "ARTICLES"
sortKey      = "ARTICLES#ART-001#SKU-7001#<uuid>"   (Testdaten)
              oder
sortKey      = "ARTICLES#<uuid>"                    (via API neu angelegt)

partitionKey = "CATALOGS"
sortKey      = "CATALOGS#GLASS#METADATA#<uuid>"
```

Alle Handler wurden daraufhin vollständig überarbeitet. Die `KeyHelper`-Klasse wurde so konzipiert, dass sie **beide Sortkey-Formate** unterstützt, indem immer das letzte `#`-Segment als UUID ausgewertet wird.

## 9. Bekannte Einschränkungen (dokumentiert, nicht behoben)

1. **Skalierung der ID-Suche:** Die `contains(sortKey, uuid)`-FilterExpression liest alle Items einer Partition und filtert dann serverseitig. Bei sehr großen Datenmengen (>10.000 Items) ist ein GSI auf einem dedizierten `articleId`-Attribut effizienter.

2. **productCount nicht atomar:** `AssignArticleToCatalogHandler` und `RemoveArticleFromCatalogHandler` führen Update-Operationen ohne DynamoDB-Transaction durch. Bei gleichzeitigen Zugriffen kann `productCount` kurzzeitig inkonsistent sein. Eine Lösung wäre die Verwendung von `TransactWriteItems`.

3. **Kein SKU-Index:** Ein ursprünglich geplanter GSI `SKU-index` ist in der CDK-verwalteten Tabelle nicht vorhanden. SKU-Suche läuft daher als FilterExpression über alle Artikel.
